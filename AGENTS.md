# AGENTS.md

Instructions for coding agents working in this repo. The rules in [Project rules](#project-rules) are the review standards.

## Project

LamedDB is an adaptive cloud-native database: one API to write and query records, publish events, and subscribe to changes, plus a hosted MCP server. It picks layout, partitioning, tier, and indexes from the workload so application code never changes. Pilot users are B2B SaaS teams building bounded workflows such as orders, tickets, and activity feeds. What exists today is a `node:http` server (`src/cli.ts`, `src/http/server.ts`) in front of `CollectionService` (`src/collections/service.ts`). Each use case is one logical request resolved by a router (`src/engine/router.ts`) through the catalog and registry onto a `Store` (`src/storage/store.ts`, with in-memory `MemoryStore` in `src/storage/memory-store.ts` and durable `PostgresStore` in `src/storage/postgres-store.ts`), plus a TypeScript SDK (`src/sdk/client.ts`, exported from `src/index.ts`) that creates a collection and puts, gets, and deletes records whose declared fields are `string`, `integer`, and `timestamp` (`src/types.ts`, checked in `src/validate.ts`). A put can require the current version with `If-Match` / `ifVersion`, and a record put accepts `Idempotency-Key`. A stored key expires after a TTL (default 24 hours, `IDEMPOTENCY_TTL_MS`) and each collection keeps at most `LIMITS.maxIdempotencyKeysPerCollection` keys (`IDEMPOTENCY_MAX_KEYS`, default 10000). The oldest key is dropped when a successful put would pass the cap. An expired or dropped key is processed again. Deleting a collection drops its keys. Every request must include `Authorization: Bearer <key>`. `src/cli.ts` reads comma-separated keys from `LAMEDDB_API_KEYS`. `listen()` takes `apiKeys` and refuses to start when that list is empty, on any host including localhost. `route()` checks the bearer token first, before the method check, the 404, and the body read, and compares keys with `crypto.timingSafeEqual`. A missing or wrong key is `401` `unauthenticated` with `WWW-Authenticate: Bearer`. The message is always `A valid API key is required.` and never contains the key. The SDK requires `LamedDBOptions.apiKey` and sends that header on every request. Listing records with paging, filters, sort and collection aliases is live (`GET /v1/collections/{name}/records`, `collection.list`; `src/collections/list-query.ts`, `src/storage/query.ts`, README "List records"). A small stdio MCP server (`src/mcp/server.ts`, `src/mcp/main.ts`, bin `lameddb-mcp`) exposes one read-only tool, `query_records`, over that list route; README "MCP tool". Other queries, event publish, change subscriptions, the hosted MCP server, idempotency for collection creation, and any durable store are not implemented yet; the live routes are `POST /v1/collections`, `DELETE /v1/collections/{name}`, `GET /v1/collections/{name}/records`, and `PUT`/`GET`/`DELETE /v1/collections/{name}/records/{id}` (`README.md`). Only that list route accepts query parameters (`limit`, `cursor`, `sort`, `filter[...]`); every other route rejects them.

## Setup and verification

Node.js 20 or newer (`engines` in `package.json`).

```bash
npm install
npm test
npm run typecheck
npm run build
npm run dev
```

- `npm test` runs `vitest run` (`vitest.config.ts`, included files `test/**/*.test.ts`).
- `npm run typecheck` runs `tsc -p tsconfig.test.json --noEmit` and covers `src/**/*.ts` and `test/**/*.ts`.
- `npm run build` runs `tsc -p tsconfig.json` and writes `dist/` from `src/**/*.ts`.
- `npm run dev` runs `tsx src/cli.ts` and listens on `http://127.0.0.1:8080`. `HOST` and `PORT` override the bind address (`src/cli.ts`; default host `127.0.0.1`, default port `8080`).
- `npm start` runs `node dist/cli.js` after `npm run build`, with the same `HOST` and `PORT` defaults.

## Project rules

### The No Silent Ignores Rule

A header, query parameter, body field, or SDK option that asks for behavior this version does not implement is rejected with `400` and `LamedError` code `invalid_argument`, and storage is left unchanged. Copy `rejectIfMatch`, `rejectIdempotencyKey`, and the unknown-key loop in `parseCreateCollectionBody` (`src/http/server.ts`): `If-Match` and `Idempotency-Key` fail on `POST /v1/collections`, and a create body may contain only `name`, `fields` and `aliases` (an alias is checked by `parseAliasDeclarations`: it cannot equal a declared field or `id`, and must point at a declared field). `If-Match` on `PUT /v1/collections/{name}/records/{id}` is one quoted version (`PutOptions.ifVersion`); a wildcard, a list, or any other shape is `invalid_argument`, and `If-Match` together with `If-None-Match` is `invalid_argument`. `Idempotency-Key` is accepted on that PUT (`PutOptions.idempotencyKey`, sent by `CollectionClient.put`) and fails on every other method, including `POST /v1/collections`, `DELETE /v1/collections/{name}`, `GET`, and `DELETE`. The two headers may be sent together. The idempotency fingerprint includes `ifVersion`, and a replay returns the original response. `If-None-Match` accepts only a bare `*` on PUT, which is `PutOptions.createOnly` (`src/types.ts`). `If-Match`, `If-None-Match`, and `Idempotency-Key` fail on `GET` and on `DELETE`. `DELETE /v1/collections/{name}` removes the collection, its records, its version counters, and its idempotency keys. `If-Match`, `If-None-Match`, `Idempotency-Key`, a query parameter, and a body on that route are `invalid_argument`, and the collection is left in place. The same rejection applies to headers, query parameters, and request bodies on every method, including methods that take no body such as `GET` and `DELETE`. An unexpected query parameter or request body is `400` `invalid_argument` before storage changes. The one exception is `GET /v1/collections/{name}/records`, which accepts exactly `limit`, `cursor`, `sort` and `filter[field]` / `filter[field][op]`; any other parameter there (including `filters` or `filterBy`) is `Unknown query parameter`, and an empty filter operator object, an empty `prefix`, or `null` with a range operator is `400` instead of being ignored. `CollectionClient.delete` takes an id and no options. Supported SDK options are `LamedDBOptions.baseUrl`, `LamedDBOptions.apiKey`, `LamedDBOptions.fetch`, `CollectionSpec.fields`, `PutOptions.createOnly`, `PutOptions.ifVersion`, and `PutOptions.idempotencyKey`. Unknown put options are rejected, including non-enumerable and symbol keys. The rule covers API semantics: preconditions, idempotency, filters, extra fields, and extra options. Transport headers the server already honors (`content-type`, `host`, `content-length`) stay as they are.

Applies to: `src/http/server.ts`, `src/http/body.ts`, `src/sdk/client.ts`, `src/types.ts`.

Why: a client that believes a guarantee (for example idempotency or a precondition) holds when it does not is worse off than one that gets an error. Origin: Day 1 Qodo review found `POST /v1/collections` silently accepted `Idempotency-Key` and `If-Match`. On PR #6, Qodo caught `DELETE` silently ignoring `?ifVersion` and a request body.

### Edge cases ship with the feature

Every new capability or fix includes tests for its failure paths — invalid input, missing resources, precondition failures, and limits — in the same change as the happy path. Cover the `400` / `404` / `409` / `412` responses the behavior can produce, and assert the stored data is unchanged when the call fails. Limits live in `LIMITS` in `src/validate.ts` (body size is 1 MiB via `src/http/body.ts`). Idempotency retention defaults are `LIMITS.idempotencyTtlMs` (24 hours) and `LIMITS.maxIdempotencyKeysPerCollection`.

Applies to: `test/**/*.test.ts` (today `test/collections.test.ts`, `test/idempotency.test.ts`, `test/idempotency-expiry.test.ts`, `test/auth.test.ts`, and `test/engine-router.test.ts`) for every change under `src/`.

Why: on Day 1 Qodo found 4 bugs, none covered by a test.

### Don't trust the types

Public exports and HTTP handlers validate input at runtime before using it. In `src/validate.ts`, `parseCollectionName` and `parseRecordId` take `unknown` and reject non-strings with `typeof`; `parseFieldDeclarations` and `validateDocument` require a plain object via `isPlainObject`. `parseCreateCollectionBody` in `src/http/server.ts` checks `body.name` with `typeof`. `readJsonBody` in `src/http/body.ts` checks `Content-Type` and `JSON.parse`. The `LamedDB` constructor in `src/sdk/client.ts` checks `baseUrl` and `apiKey` with `typeof` and rejects a missing, blank, or non-string `apiKey`, and an `apiKey` that fails `isValidApiKey`. `isValidApiKey` is true only for a non-empty printable ASCII string (`/^[\x21-\x7e]+$/`). `parseApiKeys` takes `unknown` and rejects a missing list, a non-array, an empty list, and a key that fails `isValidApiKey`. The error names the problem and does not include the key. `apiKeysFromEnv` rejects a missing, blank, or non-string `LAMEDDB_API_KEYS`, and an empty entry in the comma-separated list. `CollectionService.createCollection` passes `spec.fields` as `unknown`, and `putRecord` passes `data` as `unknown`, into those parsers (`src/collections/service.ts`). `deleteRecord` passes the collection name and record id through `parseCollectionName` and `parseRecordId`. `parseIdempotencyKey` and `parsePutOptions` take `unknown` and reject a non-string key, a key outside 1-255 printable ASCII characters, a key with leading or trailing whitespace, a non-boolean `createOnly`, an `ifVersion` that is not a non-negative safe integer, and unknown put options, including non-enumerable and symbol keys. `parseMemoryStoreOptions` takes `unknown` and rejects a non-object, a `now` that is not a function, an `idempotencyTtlMs` or `maxIdempotencyKeys` that is not a positive safe integer, and unknown store options, including non-enumerable and symbol keys. `parsePostgresStoreOptions` takes `unknown` and rejects a non-object, a missing or blank `connectionString`, a `schema` that is not a lowercase identifier, a `pool` without a connect function, a `now` that is not a function, retention that is not a positive safe integer, and unknown options, including non-enumerable and symbol keys. Those errors do not include the database URL. `databaseUrlFromEnv` rejects a non-object environment, a non-string `LAMEDDB_DATABASE_URL`, and a blank URL, and the error does not include the URL. `deleteCollection` passes the name through `parseCollectionName`, including the SDK before it builds the request path. `Router.resolve` takes the request as `unknown` and rejects a non-object, an unknown field (including non-enumerable and symbol keys), a scope other than `default`, a consistency other than `strong`, an operation outside the registry list, a collection name `parseCollectionName` rejects, and a `deadline` that is not a non-negative safe integer. A present `deadline` is not enforced. `parseServiceOptions` rejects a non-object, an unknown option, and an `onRoute` that is not a function. Values that enter through `src/index.ts`, the SDK, or HTTP get these checks even when a TypeScript signature already names a type.

Applies to: `src/index.ts`, `src/http/server.ts`, `src/http/body.ts`, `src/collections/service.ts`, `src/engine/router.ts`, `src/validate.ts`, `src/sdk/client.ts`.

Why: JavaScript callers and raw HTTP clients bypass TypeScript.

### Every error gets a response

Errors return the `LamedError.toJSON()` envelope from `src/errors.ts` and the status on `LamedError.status`. The shape is `{ "error": { "code": ErrorCode, "message": string, "details"?: object } }`. `details` is omitted when absent. Codes and statuses: `invalid_argument` 400, `unauthenticated` 401, `not_found` 404, `already_exists` 409, `idempotency_conflict` 409, `precondition_failed` 412, `method_not_allowed` 405, `internal` 500. `handleRequest` in `src/http/server.ts` writes that JSON for a `LamedError` and for any other thrown value (`internal` / 500) through `writeJson` before it returns. An oversized body (`OversizedBodyError` in `src/http/body.ts`) pauses the request, `writeJson` sends the 400, and the socket is destroyed only in the `writeJson` flush callback. A missing or wrong API key is `unauthenticated` / 401 with `WWW-Authenticate: Bearer`, and that response is flushed before the socket is destroyed. New routes must sit behind the bearer check in `route()` (the one exception is `GET /health`, which is public on purpose so load balancers and uptime checks can call it) and have a test that a missing key returns `401` `unauthenticated` before the handler reads a body or changes storage.

Applies to: `src/http/server.ts` (`handleRequest`, `writeJson`), `src/http/body.ts`, `src/errors.ts`.

Why: the client has to receive the status and the error envelope. Destroying the socket before `writeJson` finishes drops that response.

### All storage goes through `Store`

Service and HTTP code depend on the `Store` interface in `src/storage/store.ts` (`createCollection`, `getCollection`, `deleteCollection`, `putRecord`, `getRecord`, `deleteRecord`, `listRecords`). `CollectionService` takes a `Router`, or a `Store` that it wraps in a one-engine registry, catalog, and router. `listen({ store })` and `new CollectionService(store)` use that wrap. The router resolves the partition writer with `resolveWriter` and does not read `ownership`, `defaultOwnership`, or `fallbackEpochs`. It rejects a catalog that was not built with the same registry object. A record use case (`putRecord`, `getRecord`, `deleteRecord`, `listRecords`) also requires that pinned engine to list `getCollection` before any storage call, and it does not call a method the descriptor omits. `route` and `handleRequest` call `CollectionService`. `putRecord` applies the write, the `createOnly` check, the `ifVersion` check, the idempotency expiry check, and any key record in that one call. The service does not read the version, or decide that a key is live, and then write. The put carries the collection `revision` from that read, and the store rejects the write when the name now refers to a different collection. `deleteCollection` removes only that collection's records, version counters, and keys. A failed write is not stored and does not evict a live key. The key is stored per collection with the request fingerprint, the original result, and the time it was stored. A live key is replayed. An expired or evicted key is processed again. When a successful put would pass the collection cap, the oldest stored key is dropped. Replaying a key does not refresh its age or its TTL. `deleteRecord` removes the record and keeps its last version, so a later put of that id continues at last + 1, and it does not drop idempotency keys. `deleteCollection` removes the collection, its records, its version counters, and its keys. A new layout or tier is a new class under `src/storage/` that implements `Store`, passed in as `listen({ store })` or `new CollectionService(store)`. The one `MemoryStore` construction in HTTP code is the default inside `listen` (`src/http/server.ts`), used when the caller passes neither `store` nor `service`. `src/cli.ts` builds a `MemoryStore` from `IDEMPOTENCY_TTL_MS` and `IDEMPOTENCY_MAX_KEYS` when it starts the process, unless `LAMEDDB_DATABASE_URL` is set, in which case it migrates and uses `PostgresStore` behind the router. The router still resolves the writer with `resolveWriter`. The URL is never logged or placed in an error. Every new `Store` implementation must run the shared contract in `test/store-contract.ts` (`runStoreContract`) against that engine, the way `test/memory-store.contract.test.ts` does for `MemoryStore` and `test/postgres-store.contract.test.ts` does for `PostgresStore` when `LAMEDDB_TEST_DATABASE_URL` is set.

Applies to: `src/collections/service.ts`, `src/engine/router.ts`, `src/http/server.ts`, `src/storage/store.ts`, `src/storage/memory-store.ts`, `src/storage/postgres-store.ts`, `src/cli.ts`.

Why: LamedDB can later swap layouts and tiers without touching callers.

### Per-request state is bounded and cheap to trim

State that grows with each client request, such as idempotency keys, has a configurable limit, and trimming it on the write path stops at the first live entry. Records, collections, and version counters are unbounded by design, and this rule does not apply to them. The limit is `LIMITS.maxIdempotencyKeysPerCollection` and the lifetime is `LIMITS.idempotencyTtlMs`, both read by `parseMemoryStoreOptions` (`MemoryStoreOptions.maxIdempotencyKeys`, `MemoryStoreOptions.idempotencyTtlMs`). How a bad option is rejected is covered by `Don't trust the types`. `remember` (`src/storage/memory-store.ts`) keeps one map per collection in insertion order. It moves a reused key to the end, drops expired keys from the front, and stops at the first live key, then drops from the front while the map is over the cap. `storedAtFor` pins a new timestamp to `idempotencyNewestAt` when `now` is earlier than a timestamp already kept, so expiry stays a prefix and that early break still drops every expired key. `PostgresStore` does the same work inside the put transaction: rows are ordered by `stored_at` then insertion sequence, expired rows are deleted only through the first live key, and the oldest rows are dropped while the collection is over the cap. A backwards clock pins `stored_at` to the newest value already stored. The trim runs inside `Store.putRecord`. Replay, a failed write, and what delete does with keys are `All storage goes through Store`. Tests for this rule cover a full store (the collection is at its key cap and nothing has expired), expired entries, and a backwards clock (`test/idempotency-expiry.test.ts`). The other failure paths for a change are `Edge cases ship with the feature`.

- Time comes from the injected `now` (`MemoryStoreOptions.now`, `PostgresStoreOptions.now`), never raw `Date.now()` in logic. `readNow` calls that function. `parseMemoryStoreOptions` and `parsePostgresStoreOptions` pass `Date.now` only when the caller omits `now`.

Applies to: `src/storage/memory-store.ts`, `src/storage/postgres-store.ts`, `src/validate.ts`, `test/**`.

Why: each stored key keeps a copy of the document, so a client that sends a new key on every write can grow process memory while the records stay small. On https://github.com/omerts/LamedDB/pull/8, Qodo found "Server memory grows without bound per write". That finding was deferred and became https://github.com/omerts/LamedDB/issues/9. On https://github.com/omerts/LamedDB/pull/10, Qodo found that every keyed put scanned all stored keys. The fix evicts from the front and stops at the first live entry.

## Quality gate

Apply this to every task. Use Qodo Reviewer on uncommitted changes (staged and unstaged), or Review Resolver on a PR. Give the review the task requirements and the decisions made.

- Investigate every finding against the code and the requirements. Reject invalid ones with evidence.
- Fix every valid High and Medium finding, of any type (Bug, Rule violation, Requirement gap).
- Do not change code for Low findings. Report every Low finding for the owner's attention, including unchanged Low Rule violations.
- After fixes, run typecheck, tests and build, then rerun the review. Repeat until no valid High or Medium finding remains. Stop after 3 rounds.
- For a PR, the latest completed Qodo review must cover the latest commit.
- Before any merge, run the pre-merge Qodo findings check (`npm run check:qodo-findings -- --pr-url <pull request url>`, or the same check on JSON from `qodo read pr-review-session findings --pr-url <url> --extended --json` via `--file` or stdin). Do not merge while any High or Medium finding is open. Each one must be fixed or rejected with verified evidence on the pull request. The check does not dismiss findings, lower severities, or replace the other readiness gates or a human merge approval.
- Report the task as NOT DONE, with the blocker and what is needed, if a valid High or Medium finding is unresolved, checks or review are incomplete, or the loop stalls.
